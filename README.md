## Overview

This project simulates a real-world customer engagement where Nexus Consulting Group (a mid-sized management consulting firm) migrates from Smartsheet to monday.com Work Management. The solution covers end-to-end delivery: requirements analysis, data migration, validation, and a custom executive dashboard.

**Deliverables:**
1. Data migration script — parses, transforms, and loads legacy Smartsheet data into monday.com via the GraphQL API
2. Validation script — queries monday.com and compares migrated data against the source CSV, producing a validation report
3. monday vibe dashboard — custom executive dashboard for Nexus leadership
4. This documentation

## Requirements Analysis

Based on the discovery call transcript with Derek Simmons (Operations Director) and Priya Patel (Senior Project Manager), the following requirements were identified:

### Board Structure
The source data is a flat, denormalized CSV with one row per deliverable and engagement-level data repeated on every row. The migration restructures this into a fact/dimension model with two connected boards:

- **Nexus - Engagements** (dimension board) — one item per unique engagement, deduplicated from 27 source rows down to 6
- **Nexus - Deliverables** (fact board) — one item per deliverable, linked back to its parent engagement via a Connect Boards column

### Data Transformations
The source data contained inconsistent status values that were standardized during migration:

**Engagement Status → Standardized:**
| Source Value | Migrated Value |
|---|---|
| In Progress / Active / Working on it | Active |
| Complete / Done | Complete |
| On Hold | On Hold |
| Not Started | Not Started |

**Deliverable Status → Standardized:**
| Source Value | Migrated Value |
|---|---|
| To Do / Not Started | To Do |
| In Progress / Working on it | In Progress |
| In Review | In Review |
| Done / Complete | Done |

### Key Design Decisions
- Engagements and Deliverables are maintained as separate boards and linked via monday.com's item-link column type, reflecting the relational structure Derek and Priya described
- Status columns use distinct labels between the two boards to avoid confusion (engagement "Active" ≠ deliverable "In Progress")
- Budget is stored as a numbers column on the Engagements board
- Estimated hours is stored as a numbers column on the Deliverables board
- All date fields are formatted to monday.com's expected format during transformation

## Part 1: Data Migration

### How to Run

```bash
# Install dependencies
pip install -r requirements.txt

# Add your monday.com API token to .env (see env.example)
# MONDAY_API_TOKEN=your_token_here

# Phase 1 — creates boards and columns, writes board_config.json
python migration.py --phase 1

# ⚠️ MANUAL STEP required between phases:
# In the monday.com UI, add a Connect Boards column to the Deliverables board
# and link it to the Engagements board.
# This step is required because the monday.com API does not support creating
# board_relation (Connect Boards) columns programmatically.
# Reference: https://developer.monday.com/api-reference/reference/connect

# Phase 2 — loads all data and establishes board relationships
python migration.py --phase 2
```

### What the Script Does

The migration is split into two phases due to an API limitation with Connect Boards columns:

**Phase 1:**
1. Reads `nexus_smartsheet_export.csv`
2. Deduplicates rows to extract 6 unique engagements from 27 deliverable rows
3. Creates the Engagements board with all required columns
4. Creates the Deliverables board with all required columns
5. Writes `board_config.json` incrementally (after each board) so a failed run preserves created board IDs

**Phase 2:**
1. Reads `board_config.json` for board/column IDs
2. Normalizes status fields for both engagements and deliverables
3. Loads all 6 engagements into the Engagements board
4. Loads all 27 deliverables into the Deliverables board
5. Links each deliverable to its parent engagement via the Connect Boards column

### Assumptions
- Connect Boards column is added manually in the monday.com UI between Phase 1 and Phase 2 (API limitation — documented in session_notes.md)
- All dates in the source CSV are in MM/DD/YYYY format and are converted to YYYY-MM-DD for the API
- Status labels are created on first use via `create_labels_if_missing: true` in the GraphQL mutation
- The default "Task 1" placeholder item created by monday on new boards is suppressed using `empty: true` in the `create_board` mutation

## Part 2: Migration Validation

### How to Run
```bash
python validate.py
```

### What the Script Checks
- **Row counts** — total engagements and deliverables in monday.com match source CSV (6 engagements, 27 deliverables)
- **Engagement ID coverage** — all engagement IDs from source are present in monday.com
- **Deliverable ID coverage** — all deliverable IDs from source are present in monday.com
- **Orphaned deliverables** — any deliverable missing a linked engagement (uses GraphQL inline fragment on `BoardRelationValue` to correctly detect links)
- **Missing required fields** — deliverables without an assignee or due date flagged for cleanup
- **Status normalization** — confirms no raw/unmapped status values remain in either board

### Validation Results
All 8 checks passed on final run:

| Check | Result |
|-------|--------|
| Engagement count (expected 6, got 6) | ✅ PASS |
| Deliverable count (expected 27, got 27) | ✅ PASS |
| All engagement IDs present | ✅ PASS |
| All deliverable IDs present | ✅ PASS |
| No orphaned deliverables | ✅ PASS |
| Required deliverable fields populated | ✅ PASS |
| Engagement status normalization | ✅ PASS |

Full output available in `validation_report.json` and `console_output.md`.

## Part 3: monday vibe Dashboard

The custom dashboard was built using monday vibe inside the monday.com trial account and remains in draft mode as instructed.

### Dashboard Components
- **Active Engagements** — filtered view of all engagements with Active status
- **Deliverable Status Breakdown** — chart showing distribution of deliverables across To Do / In Progress / In Review / Done
- **Bottleneck Indicator** — highlights deliverables stuck in "In Review" status
- **Work Distribution by Lead** — breakdown of deliverable workload across team members
- **Upcoming Due Dates** — deliverables with due dates in the next 30 days

### How It Addresses Derek & Priya's Requirements
- Derek can open monday.com and immediately see which engagements are active and overall delivery health — no pivot table required
- Priya can pull up the dashboard in Monday morning team meetings for an instant status snapshot
- Leadership can access the live dashboard directly — no exporting needed

## AI-Assisted Development

AI tools were used throughout this assignment as a core part of the workflow — consistent with how a Technical Consultant would operate on a real engagement.

### Tools Used
- **Claude (claude.ai + VS Code extension)** — primary development partner for script generation, debugging, and iteration
- **monday.com API documentation** — referenced throughout for GraphQL query structure, field types, and API limitations

### How AI Was Used
- Generated the initial migration script structure based on discovery call requirements
- Iterated on GraphQL mutation syntax when API calls returned errors
- Debugged status normalization logic and data transformation edge cases
- Identified and resolved rate limiting issues with exponential backoff retry logic
- Generated the validation script framework including the GraphQL inline fragment pattern for board relation columns
- Helped interpret API error messages and identify root causes

### Key Iterations & Learnings
A detailed prompt log and iteration history is documented in `session_notes.md`. Notable examples:

- **API limitation discovery:** AI initially suggested `connect_boards` as the column type, which returned a 400 error. Iterated to discover `board_relation` is the correct enum — then discovered board_relation columns can't be created via API at all, leading to the two-phase architecture
- **Rate limiting:** Hit 429 errors during column creation. AI helped implement exponential backoff (10s → 20s → 40s) and increase baseline delay between calls
- **Orphaned deliverable false positive:** Validation was incorrectly flagging all deliverables as orphans because `board_relation` columns don't populate standard `text`/`value` fields. Resolved by using a GraphQL inline fragment (`... on BoardRelationValue { linked_items { id } }`)
- **Incremental config writes:** Early crash during column creation left boards created with no ID record. Redesigned config write to be incremental after each board

### Honest Assessment of AI Limitations
- AI-generated GraphQL mutations occasionally used incorrect or deprecated field names requiring correction against live API docs
- The Connect Boards API limitation required human research to confirm — AI's initial suggestion was technically wrong
- Validation logic edge cases (especially around board_relation column structure) required iterative debugging that AI alone couldn't resolve without error output to work from
